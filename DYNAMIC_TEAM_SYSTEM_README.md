# Dynamic Team System — Player Portal Operation: Surabaya

## Implemented behavior

- Create Room starts with RED and BLUE. Host can add GREEN and YELLOW in that order, set each capacity (1–50), and remove the last additional team.
- Team labels and HEX colors are generated by the system; the Host only chooses which configured team to join as.
- Join Room and Room Browser display each room's configured teams, player count, capacity, and full/available state.
- Waiting Lobby renders all configured teams and their players from the API response.
- Backend validates that a selected team belongs to that room and uses a database RPC that serializes joins on the match row before enforcing capacity.
- Match history and gameplay analytics include per-team summaries. Base Shutdown and Healing accept the four catalog teams, and a station can only target a team configured in that room.

## Supabase migration order

1. If these feature tables have not already been installed, run the existing `base_shutdown_migration.sql` and `healing_system_migration.sql` first.
2. Run `dynamic_team_system_migration.sql` in Supabase SQL Editor.
3. The migration adds the room/team relation, seeds the four shared team definitions, backfills existing matches as RED/BLUE, expands station/winner constraints, and installs `join_match_team` for capacity-safe joins.
4. Deploy the updated FastAPI application and Player Portal assets together.

The migration intentionally keeps `matches.red_capacity` and `matches.blue_capacity` populated for legacy consumers; the authoritative dynamic configuration is `match_teams`.

## Base QR payloads

Base Shutdown payloads: `OPS-BASE-SHUTDOWN:BASE-RED`, `...:BASE-BLUE`, `...:BASE-GREEN`, `...:BASE-YELLOW`.

Healing payloads use the corresponding station code, e.g. `OPS-HEALING:BASE-GREEN`. The migration creates the database station records. Physical QR artwork for the four newly added teams still needs to be printed/generated for field use; the existing RED/BLUE QR artwork remains unchanged.

## Upgrade from the previously deployed six-team build

If the earlier six-team migration has already been run in Supabase, do **not** rerun the full `dynamic_team_system_migration.sql`. Run `four_team_limit_migration.sql` once instead. It disables legacy PURPLE/ORANGE base and healing stations while retaining their catalog/history rows to avoid breaking existing references. The updated API and Player Portal only expose RED, BLUE, GREEN, and YELLOW for new rooms.
